# Several profiles, and a .deckyprofile that carries everything a profile needs

**Context:** Decky has one profile, `decky.json`, and Settings can export it as
plain JSON and import it back over the top. That JSON names scripts and images
by absolute path, so it is only a profile on the PC it came from, and importing
replaces what you had. The user wants several profiles, switched only after
looking inside one, and a single file they can hand to someone else that brings
the whole setup with it: scripts, artwork, the lot.

## What a profile is

`%APPDATA%/Decky/profiles/<id>/`, one folder each:

```text
profiles.json            the list, and which is active
profiles/<id>/
  profile.json           pages and keys - today's decky.json
  widgets.json           counters, timers, the last dice roll
  integrations/*.json    one per app Decky talks to
  files/                 scripts and images the keys use
```

Kept out of profiles, because they belong to this PC and not to a setup: the
deck's Wi-Fi pairing, the window's own settings, update state. Switching
profiles never logs the deck out of anything.

Today's `decky.json` becomes `profiles/default/profile.json` the first time the
new build starts, and the old file is left where it is.

## The file

`<name>.deckyprofile`: a header (`DECKY`, a format number), a random salt and
IV, then the archive encrypted with AES-256-GCM. Inside: `meta.json` (name,
when, the Decky and protocol versions it came from, and counts), `profile.json`,
`integrations/`, and `files/`.

The key is derived from a constant inside Decky. **This is obfuscation, not
secrecy** - any copy of Decky opens any `.deckyprofile`, which is what "only
Decky can read it" means in practice. It stops the file being edited in a text
editor and makes it clearly Decky's. The UI says as much where it matters, and
credentials never go in at all (below).

Windows learns the extension from the installer (`fileAssociations`, icon built
from `Branding/decky-profile.png`), and the app registers it under HKCU when it
starts so a `pnpm dev` build behaves the same. Double-clicking one starts Decky
if it is closed, or wakes the running one through the single-instance lock it
already has; either way the file waits until the deck has finished loading, and
then Decky asks.

## It must catch new things by itself

The rule for everything below: **one declaration, where the thing is declared;
the profile machinery only walks the registries.** Adding a widget, an action, a
credential or an integration must not mean remembering to edit an export list.

- **Files a key uses.** Each action kind already declares how it is validated
  (`ACTION_CHECKS`); it now declares its file fields beside that. The bundler
  asks each kind for the paths in an action and for a copy of it with new paths,
  so it can rewrite them on import. The table is a mapped type over the action
  kinds, so a new kind **does not compile** until it says whether it has files.
  Widget kinds get the same optional hook.
- **Integrations.** The bundle walks `Object.keys(integrations)`, so a new app
  is carried the day it exists. Each service declares which of its settings are
  secret; those are dropped from an export and asked for again after an import.
  Same mapped type, same compile-time nag.
- **Everything else in the profile** travels as the JSON it already is, so a new
  field on a key, or a new widget type, rides along with no change here at all.
  `validateConfig` and `retireWidget` decide what survives the trip back.

## Looking before you leap

One inspector, used for both importing a file and switching to a stored profile.
It shows: where it came from and when, its pages and keys, its widgets by type -
**including the ones this Decky no longer has, named and counted, with the keys
that will be dropped** - the files it carries, and every program and script a
key would run. That last list is the point: a `.deckyprofile` is someone else's
setup, and it can point keys at executables. Nothing is written until the button
is pressed.

Importing always **adds a profile**; it never overwrites the one in use. Its
files land in the new profile's own folder and its keys are rewritten to point
there, so the profile works on a PC that has never seen those paths, and
deleting the profile takes its files with it. Programs (`.exe` you launch) are
recorded by path, not copied.

**Rejected:**

- _A password on the file._ Real secrecy, but it has to travel with the file
  anyway, and a lost password is a lost profile. Offered later if wanted.
- _Restoring files to the paths they had._ Exact on the machine it came from,
  and wrong everywhere else - it writes into folders that may belong to someone
  else.
- _Importing over the current profile._ A double-clicked file should never be
  able to wipe the setup you are using.
- _A hand-kept list of what to export._ It is wrong the first time someone adds
  a widget and forgets, and the failure is silent: a profile that quietly leaves
  something behind.
