## Panel brought up, grid test flashed

The board is alive and now runs our own firmware. Working tree gained
`firmware` (PlatformIO project) and `firmware/factory-backup`
(4 MB image of the shipped flash, read off before erasing).

Getting it to enumerate took most of the session. It did not appear on USB at
all — not even as an unknown device — while the screen was clearly powered. The
CH341SER driver was genuinely missing, but that turned out to be a *consequence*
rather than the cause: Windows only pulls the CH340 driver once the device shows
up. Installing it changed nothing; the port appeared only after the cable was
dealt with. Worth remembering that "no device at all" points at the cable, while
"device with a yellow bang" points at the driver.

Second snag: `read-flash` at the board definition's default 921600 baud returned
corrupt data. 460800 worked and is now pinned.

The firmware itself came up first try — panel init, grid drawn, no VSYNC
timeout. The rendered boundaries close flush on 0 and 800/480, which confirms
the active-area assumption baked into the Fusion design.

## Flicker traced to pixel clock, not to the panel

The first flashed build showed flickering lines *inside* the left-hand cells.
Two things were wrong, and separating them mattered:

1. **Pixel clock too high.** 24 MHz starved the scanline DMA. Dropping to the
   15 MHz in Elecrow's readme fixed it outright. Their own LVGL example uses
   24 MHz, so copying that example's value was the mistake.
2. **Second frame buffer never populated.** Instrumentation that read both
   buffers back showed `lit fb0=14224, lit fb1=0` — the entire grid lived in one
   buffer only. Not what caused the visible flicker, but it would have blanked
   the screen on any buffer switch. Fixed by mirroring fb0 into fb1; verified
   `buffer diff total: 0 px`.

Worth keeping: the symptom that cracked this was "same cells always, background
clean". A moving artefact with a noisy background would have meant bandwidth
starvation of a different kind; a fixed one pointed at timing.

The read-back also confirmed the geometry: 948 lit pixels per cell is exactly the
two-pixel border of a 118x123 rectangle.

Decisions: [[panel-pclk-limit]]

## Firmware given a real structure, and a power cut ate nine notes

The firmware project was renamed from `grid-test` to `streamdeck` — the working
name, not a final one — and split out of its single file:

- `lib/panel` — RGB bus, timing, backlight, frame buffers. The only code that
  knows GPIO numbers.
- `lib/keygrid` — the 5 x 3 layout and the millimetre-to-pixel conversion, kept
  in one place because the panel's pixels are not square and every consumer
  needs both scales.
- `src/main.cpp` — the current screen, which is still the alignment test.

Rebuilt and reflashed; the serial report is byte-identical to before the split
and the frame buffers still differ by zero pixels, so the restructure changed nothing
observable.

Then mains power dropped. Nine `notes/memory/` files came back as pure
whitespace with their byte counts intact — an unflushed-write casualty, the
classic unclean-NTFS-shutdown signature. All nine were rewritten from the
session transcript. The firmware sources, the journal, the decisions note and
`MEMORY.md` survived untouched.

Open: this repo is still not under version control, which is the only reason the
loss needed manual recovery.

## Fifteen animations, and the refresh rate that was never the panel's fault

Put a different animated GIF in each of the 15 key openings as a load test. The
question was whether fifteen concurrent decoders are viable at all; they are,
comfortably. Assets are generated by `tools/make_gifs.py` (Pillow) and compiled
in as C arrays.

The interesting part was the refresh rate. It looked low because it was: 30.8 Hz,
which is what 15 MHz pixel clock buys at this panel's blanking. 15 MHz had been
adopted as the panel's limit after 24 MHz produced flickering lines — but the
limit was never the pixel clock. It was Elecrow's 10-line bounce buffer, too thin
to absorb PSRAM contention. Widening it to 40 lines made 24 MHz clean under full
load: **49.3 Hz, and 15 GIFs still decoding**. The earlier note claiming a 15 MHz
ceiling has been rewritten; it was costing 40% of the refresh rate.

Then tearing showed up — reported precisely enough to diagnose from the
description alone ("the bottom 30% of the line runs ahead"). Fixed by tracking
the beam and writing each cell only when the scanout is clear of it. Double
buffering would have been the expensive wrong answer: a 768 KB copy per refresh
would have spent exactly the PSRAM bandwidth that was just recovered. Turbo
decoding is what made the cheap fix possible — a cell write dropped from ~2.4 ms
to ~0.6 ms, small enough to fit between beam passes. I had dismissed turbo mode
as pointless a few minutes earlier, on the grounds that decode throughput was
already 15× what was needed. Throughput was the wrong metric; latency was the one
that mattered.

Also shipped: the generator now writes the real `.gif` files to `assets/gifs/`
instead of only emitting C arrays. It had been producing a working system with
nothing a human could open, which is how a build ends up unfalsifiable.

Last pass made the motion smooth rather than fast, on request: 16 frames over
0.53 s became 48 over 1.92 s, so the sweeping bar steps 2.5 px instead of 7.4 px.
Two animations that were choppy by design (a blinking cross, a flipping
checkerboard) were replaced with continuous ones. Two others only had 16 and 24
distinct frames because they scroll a repeating pattern on whole-pixel offsets —
drifting them through several pattern periods per loop restored the frame count
without changing the look.

Open: still no way to use an externally supplied GIF — the generator draws them,
it does not ingest them. And the repo is still not under version control.

## Three bugs that all reported success

The animation test went wrong three times in a row, and every one of them showed
healthy numbers while the panel was wrong.

**Blank cells.** Turbo decoding only invokes the draw callback when the draw type
is cooked *and* a canvas has been allocated. Neither was true, so `playFrame()`
returned success, the frame counter climbed, and nothing was written to the
screen. Worse, the "2.4 ms to 0.8 ms" speedup I had reported as a win was
measuring a decoder that had stopped drawing. Fixed by meeting the contract
(`allocFrameBuf` + `GIF_DRAW_COOKED`), which also turns the callback into a
straight copy. Real cost with turbo is ~1.9 ms, and ~4.0 ms once frames became
full-canvas.

The instrument that was missing: frames decoded and scanlines written are now
counted separately. One number could not distinguish "working" from "drawing
nothing", and that is precisely the state it was in.

**Ghosting.** Frames were encoded as differences with transparent unchanged
pixels, so anything that desynchronised the decoder's canvas from the panel left
trails. Switched to full frames. `optimize=False` was not enough - Pillow's frame
differencing is separate from palette optimisation and `disposal=2` is what
disables it. Full frames turned out to encode *smaller* here, so the diffs had
been buying nothing at all.

**Stutter.** Reported per-animation, which made it diagnosable: the bouncing ball
and pulsing square stuck, the sweeping bar and equaliser were smooth. Two
distinct causes. Eased motion crawls at its turning points until consecutive
frames round to identical pixels and get merged into one long frame - a real
pause. And the rotating hand had every frame distinct but moved 6.5 px per step
at the tip against the smooth bar's 2.5 px.

Fixed with constant-rate motion and 72 frames, and the generator now reports
distinct-frames-vs-requested. It immediately caught two more I had not noticed.
One of them was not fixable as designed: a pattern repeating every 16 px can only
ever produce 16 distinct frames however far it scrolls, so `concentric` was
replaced with rotating nested squares.

Settled at 15.3 fps per cell, paced to the ~16 fps ceiling that 4 ms per full
frame across fifteen cells allows, so frames land evenly instead of late.

**Also:** the board's boot loop earlier was a hung `esptool` - a background
upload stuck mid-write for ten minutes, leaving the app partition half erased.
Killing an upload mid-write is how that happens; wait for it or stop it
deliberately, then reflash.

## Live content push, and a decoder that invents colours

The imported GIF glitched - cyan streaks and red pixels that never cleared - and
the way in was to stop describing it and read the panel back. `tools/dump_cell.py`
pulls a key's pixels off the board over serial, so the artefact could be measured
rather than reported: the bad pixels were **in the frame buffer**, which killed
the DMA-starvation theory outright, and the offending colours appear **nowhere in
the source file**.

Bisected from there. Turbo mode off: still corrupt. The library's raw draw path
instead of its cooked one: still corrupt. Our own writes clamped to the cell and
counted: zero escapes. That leaves the LZW decode of difference-encoded frames,
which is not something a caller can configure around. Re-encoding the same file
as full frames rendered it clean - so imported GIFs are now re-encoded rather
than embedded as found.

Two earlier theories died here, both mine: that the artefacts were DMA
contention (they were in memory), and that they were out-of-bounds writes (the
counter said zero).

Then built what was asked for: `tools/push_media.py` puts any image or animation
on any key over the serial port, no reflash. Stills and animations share one
format - a still is a one-frame GIF - so there is one decoder and one class of
bug, and a still costs no CPU once drawn.

The transfer took three measurements to get right. Streaming lost ~110 bytes near
the end; 256-byte blocks still lost bytes; 128-byte blocks arrive intact, which
is exactly the hardware FIFO size. Then the first working version ran at 43 bytes
a second, because the firmware was still waiting for 1024-byte blocks and timing
out on each one. Matching both ends took a 200 KB push from 93 seconds to 8.

A quieter bug surfaced only because a number looked wrong: 151 frames encoding to
3.9 KB. `list(ImageSequence.Iterator(im))` returns many references to one image
object, all sitting on the last frame - so every frame was identical. Fixed by
converting each frame while it is current.

Verified by reading the panel back: a pushed still image renders with its exact
colours, within RGB565 rounding.

## Storage: the 4 MB ceiling, and the card that removes it

Questioned whether the board really only has 4 MB, and asked the chip rather than
trusting the module marking: `esptool flash-id` reports device 0xc84016,
"Detected flash size: 4MB". It is a hard limit. After the bootloader, a 2 MB
application and housekeeping, about 1.9 MB was left for content - enough for one
page of 15 keys, not enough for the multi-page deck this is meant to become.

The panel has a TF slot. Elecrow's wiki gives its pins (MOSI 11, MISO 13, CLK 12,
CS 10, no DIP switch on the Basic model) and they mounted a 16 GB card first try,
so they are now confirmed rather than documented. That ends the storage question
entirely: gigabytes instead of megabytes.

Pushed content now lives on the card at `/sd/deck/k<cell>.gif` and is reloaded at
boot. Verified properly - pushed a still and an animation, reset the board, and
read the panel back: `restored 2 key(s)`, and the pixel counts matched the
pre-reset dump exactly.

That readback also settled a loose end. A patch of cream pixels had appeared in
every dump; after the reboot it swapped places with black. So it is the status
report sharing the serial port and corrupting the binary stream - a fault in the
measuring tool, not on the glass. Worth remembering that the instrument had its
own artefact while it was being used to hunt someone else's.

**Workflow:** `pio run -t upload` hung for minutes three separate times, once
leaving the app partition half erased and the board in a boot loop. It is
abandoned. `tools/flash.ps1` drives esptool directly - 37 s for an app-only
flash, 46 s with `-Full` for bootloader and partition table - and has never hung.

## Decoding moved off the deck entirely

The suggestion was better than the plan it replaced: instead of decoding each
animation once on the board, decode on the PC and send finished frames. The deck
now runs no decoder at all - it copies palette indices through a lookup table.

Measured, all fifteen keys: per-frame cost **4.3 ms to 1.3 ms**, decode time
**2.9 ms to 3 us**, core load **90% to 37%**.

Getting there turned up four things worth keeping:

**The PSRAM "leak" was my own prebake.** 3.3 MB unaccounted for at boot turned
out to be a feature I had written and wired in, doing exactly what it was told.
Instrumenting each boot stage found it in one run; theorising about it had not.

**Uploads write straight to the card now.** Buffering the whole payload in PSRAM
was what capped animation length. A 151-frame clip at full cell size is 2.2 MB
and now works - it simply plays from the card instead of from memory, and the
firmware decides which without being told.

**The card reads at 383 KB/s and nothing shifts it.** Read sizes from 14 KB to
112 KB: 382, 382, 382, 383. SDSPI clock 20 MHz against 40 MHz: 386 against 383.
Both measured before building anything on top of them - read-ahead buffering
would have bought nothing, and I would have built it.

**Streaming belongs on the second core.** Earlier, splitting decode work across
both cores broke the panel by starving its DMA of PSRAM. Streaming is the
opposite load - it waits on SPI and barely touches memory - so the same second
core that was useless for decoding took a streamed frame from 41 ms to 26 ms.
The lesson is that "use both cores" was never the right question; what competes
for PSRAM is.

Also fixed: filling memory to the brim left 283 KB free, and the board rebooted
into a state where nothing loaded at all. There is now a 768 KB floor - content
that would cross it streams. Verified stable: 45 seconds, 23 reports, no reboots.
