## Firmware from the app, encrypted Wi-Fi, USB first

The desktop app now installs the deck's firmware itself: Settings → Firmware for updates, and the Disconnected page for a board still on factory firmware. esptool-js was proven on the real board before anything depended on it - ESP32-S3 rev 0.2, flash ID 0x1640c8, four images written and MD5-verified at 460800 baud in 20.8 s. That test found two faults that would have made healthy decks look dead: `serialport`'s `set()` asserts any line left out, and esptool-js 0.6.1's `after("hard_reset")` never resets the chip. Both are handled; the user then installed the protocol-7 firmware from Settings on hardware. Decisions: [[2026-09-10-desktop-flasher]].

Wi-Fi traffic after pairing is AES-128-GCM framed, protocol 7, and the desktop refuses plain-text firmware over Wi-Fi. Covered by framing tests and a fake deck; against the real firmware it still awaits the deck losing its cable while powered. Decisions: [[2026-09-10-encrypted-wifi]].

The connection rule changed several times in one afternoon before settling on USB first, Wi-Fi only without a cable, no manual switch. Decisions: [[2026-09-10-usb-first]].

Also: the CH340 wedged mid-session (Windows error 31 on open) and needed a replug; the Firmware section kept its "installed, restarting" message after the deck came back, fixed by keying it to the deck's firmware; flash-layout wording claimed artwork lived in the flash data partition, when it is on the microSD card.

Unplugging the deck left the app on the dashboard, and it never fell back to Wi-Fi (the user's power-bank test). Cause, measured on the deck with a script using the app's own `DeckLink`: the serial library closed the port about 1 s after the unplug, but the link kept the dead port object, and the next heartbeat PING's write waited forever. That stalled the single serial queue, so status checks and reconnects never ran again. Fix: drop the port on `close` and refuse writes to a closed port; a unit test reproduces the stall with a fake port. The user confirmed the Disconnected page and the Wi-Fi fallback both work after the fix. The deck was reachable over Wi-Fi throughout (discovery reply and `aesgcm1` challenge at 192.168.1.20).

## Build speed and installer size

Measured before changing anything:

- A release took about 7 minutes. In the firmware job, 159 of 226 s went to PlatformIO downloading and unpacking. The desktop job spent 60 s in electron-builder, 41 s of it 7-Zip.
- Every new firmware version recompiled all 194 files, because the version was a compiler flag. It is now a generated header: a new version rebuilds `main.cpp` alone, 17 s instead of 58 s.
- A clean local firmware build takes 60 s whether it uses 4 or 12 jobs. The time is not CPU-bound, so Elecrow's cap of 4 stays.

The same measuring turned up a real bug: the installed app never had the 3D model. electron-builder drops `*.obj` from packages by default, and the Disconnected page quietly fell back to its still image. The model is now a GLB made from the CAD OBJ: the same float32 vertices bit for bit, 1.37 MB instead of 6.3 MB, parsed in 4.5 ms instead of about 100 ms. Its headless-Chrome render is byte-identical to the OBJ's. A new `scripts/package-check.mjs` compares the build output with `app.asar` and now runs in the release.

Installer changes:

- English-only Chromium locales, and only the win32-x64 serial binding.
- No source maps, serialport C++ sources or node-addon-api.
- esptool-js moved to devDependencies; the main bundle is byte-identical.
- Lossless WebP for the two backgrounds: pixel-exact. They are dithered, so lossy WebP was rejected.

Results: the installer went from 116.2 MB to 106.3 MB (with the model now included), unpacked from 383 MB to 330 MB, and local electron-builder from 31 s to 23 s. The packaged `Decky.exe` was launched against the deck: UI in 0.97 s, model rendered from the asar at 1.24 s, deck connected over USB. That test used a separate user-data folder and changed nothing of the user's.

CI changes, not yet run on GitHub:

- Unchanged firmware reuses the released zip after checking its SHA-256. Tested against the real releases: 0.1.2 from v0.2.3 and 0.1.1 from v0.2.2; a missing version and a corrupted image both fall back to building.
- Firmware builds cache `~/.platformio` and the libraries.

Solid 7z compression would save 9.7 MiB more but costs about 53 s locally and several times that on CI. It was left off, as recorded in [[2026-09-10-build-speed-and-size]]. The next push releases firmware 0.1.3, so it builds with a cold cache; the reuse path first runs on a desktop-only release.

Differential updates are on; the user accepted a fourth release file ("if download faster okay no problem"). Releases now carry the installer's `.blockmap`, and the app no longer disables differential downloads. Tested between two real local installers, 0.2.0 and 0.2.1 (app code and version changed), through the real electron-updater and Decky's `installAppUpdate`, against a local server that answers single-range requests like GitHub's. The update fetched 3.2 MB of the 101.4 MB installer, in 42 requests, and the result was identical to 0.2.1. With the old installer missing from the cache, it fell back to the full 101.4 MB, again identical. The user's installed 0.2.3 did leave `installer.exe` in `%LOCALAPPDATA%\decky-updater`. The first real differential update is from 0.2.4 onward, because 0.2.3 has it disabled and its release has no blockmap. Solid 7z compression stays off; it would defeat the blockmap.
