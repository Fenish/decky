# 2026-09-11

Decky 0.2.4 with firmware 0.1.3 released overnight: 6 min 43 s end to end,
including a cold-cache firmware build. It has four files: the installer (106.3
MB), its blockmap, `latest.yml` and the firmware zip.

The README plays the demo video. GitHub strips `<video>` tags pointing into the
repository, so the user uploaded it as a GitHub attachment instead. The upload
was compressed from 41 MB to 9.3 MB (720p60, SSIM 0.998) to fit the 10 MB limit
for attachments on free accounts. Both MP4s were committed by the user anyway.

## First install over factory firmware

The board was restored to Elecrow's factory firmware from
`factory-backup/crowpanel7-factory-4MB.bin`, leaving NVS alone so Wi-Fi and
pairing survived. The factory image boots its LVGL Widgets Demo and never
answers `ID`. Its partition table differs from Decky's: app0 is 3840 KB against
2048 KB, with NVS at the same place.

What the user saw, and what changed:

- **The card showed up 12-16 s after plugging in.** A silent port is now asked
  twice a second apart within one status check, and a newly plugged-in port
  triggers a check within a second. Estimated now: about 6 s, with Wi-Fi tried
  first for a paired deck.
- **Four steps became one question,** "Install Decky on this device?". The click
  checks it is a CrowPanel and installs; anything else is left untouched. It
  still waits for the click, because the check restarts the device. The card was
  redesigned, and "Looking for Decky…" hides while it shows.
- **The install message showed the git version.** It now uses the same plain
  number as the rest of the app; `formatVersion` moved to
  `src/shared/firmware.ts`.

## The picture slip, found

After the first install the picture sat 48 lines too high, wrapped. On the
slipped deck, `DISPLAY_RESYNC` (`esp_lcd_panel_init`) left it shifted, which
disproved the earlier realign theory.

Diagnostic firmware read the RGB driver's private bookkeeping at every VSYNC:

- **Correct state:** `pos=76800`, 10 EOFs per frame, even count.
- **Provoking it:** random 30 ms flash erases on the unused data partition
  showed frames losing EOFs (as few as 1 per frame). By the second stall the
  picture stayed slipped, with an odd count and nothing else different.
- **Nudging the count by one** straightened it, confirmed on the screen.

The v5.5.4 source explains why the slip lasts: with RESTART_IN_VSYNC, the driver
never zeroes the count. The fix zeroes it in our VSYNC callback. It survived 40
random stalls with 75 corrections, and a first install through the app now
leaves the picture straight, confirmed by the user. The old realign calls are
gone; `DISPLAY_STATE` stays for diagnosis. The user had also found a forum
thread describing the same drift and blaming bounce-buffer synchronisation. See
[[2026-09-11-bounce-parity-guard]].

## Page switching

The user felt page switches as "not instant". Measured with a temporary
benchmark on the deck, a full page redraw took 83 ms. About 45 ms of that was
copying: each key was copied pixel by pixel with an integer division per pixel.
The rest was waiting on the beam. Two firmware changes:

- **Line-by-line copy:** each key row goes with one memcpy (or a column table
  for off-size cells). That brought the redraw to 61 ms; a key write now costs
  about 2.1 ms, the PSRAM-to-PSRAM floor beside the scanout.
- **Greedy order:** keys are drawn as soon as their row is clear of the beam,
  instead of in index order. That brought it to 35 ms.

The write estimate now eases back down instead of only ratcheting up.
`DISPLAY_STATE` reports the last redraw as `draw=`. The user confirmed switches
feel instant.

Back-to-Home still lagged slightly. With protocol 4 and later, opening a page
was `CACHE`, then an `ALT` check per toggle key, then `STATE`, each a Wi-Fi
round trip: 4 for Home with two Discord toggles, against 2 for other pages. The
app now remembers the pages and the ON artwork it confirmed on the deck this
session, and opens those with a single `STATE`. If the deck has dropped the
page, `STATE` is refused and the full exchange runs.

## Widgets

Widget keys: clock (digital, analog or minimal; 12/24-hour; seconds; date; time
zone), timer, pomodoro, countdown, counter, ping and note, each with its own
settings, under a Widgets group in the action picker. The desktop draws them.
Pages carry time-free base pictures, and the deck gets `LIVE` tile patches while
a page is shown. Firmware 0.1.4-dirty on COM5 reports `live=1` and passed a
hardware script: 21 ms for a small patch, about 94 ms for the worst seconds
change, and a wrong base refused. A critic reviewed the transport; see
[[2026-09-11-widgets-live-patches]].

Feedback from the user testing it in the dev app:

- **12-hour time dropped the leading zero** ("2:39" beside "02:39"). Hours are
  two digits in both formats now, in the minimal style too.
- **A moved widget appeared twice on the deck,** once in the app. A digital
  clock's base picture is only its background, like an empty key's, so the move
  changed neither the page's signature nor any picture. The deck's copy kept the
  clock drawn by patches. The app now tracks patched keys per deck copy: it
  re-sends them on rebuilds and restores them on cached pages. A simulated-deck
  test reproduces the bug.
- **Holds waited for the release.** A hold now acts the moment the press reaches
  600 ms, so a stopwatch shows its reset under the finger.
- **"Server status" became "Ping"**, for everyday use. ICMP to the internet
  never answers on this PC, which is behind a VPN adapter, while TCP to port 443
  answers in 16-46 ms. So the widget times a TCP handshake, with a second one
  raced after 500 ms because 1 handshake in 30 was lost, and falls back to
  ping.exe for hosts that answer no TCP. The router answered that way in 1 ms.

## The wheel moves onto the deck

The user wanted the countdown wheel to follow the finger in real time, with
iPhone-style momentum and snapping. App-drawn steps "teleported": each patch
takes 40-130 ms over USB. The user set a rule: animated or heavy keys run on the
deck, static or occasional ones in the app ([[deck-first-for-animation]]).

- **Built:** `firmware/src/wheel.cpp`.
  - **The look:** the desktop sends it once (`WHEEL`). It holds the key picture
    under the numbers as a `LIVE` patch, the digits at two sizes rasterised in
    the app's Segoe UI (not embedding the font), the 89 labels, and the drum and
    physics settings. The deck keeps four looks by CRC, and `WHEELAT` re-arms
    one with a single line.
  - **Drawing:** the deck draws a drum (labels at `row/angle · sin θ`, squashed
    by `cos θ`, faded by `cos² θ`) that follows the finger 1:1.
  - **Motion:** a flick glides with exponential decay (τ 0.32 s) until below 4
    labels/s. A critically damped spring (ω 16) then lands it on a label, and it
    bounces at the ends. It reports `EV … WHEEL <label>` when it stops.
  - **Tearing:** frames are composed before the beam check, so only the copy has
    to fit between the beam's passes.
- **Measured on the deck** with the real 15 KB look generated by the app's code:
  - the upload took 1.06 s over USB; each frame composes in 4.3 ms, at 61-67
    fps;
  - `WHEELSPIN` +30/s moved 9 labels and settled in 1.08 s;
  - −60/s ran into the start, bounced and settled in 1.22 s;
  - a mid-spin screen capture shows two rows straddling the band, so the motion
    is continuous, not stepped.
- **App:**
  - an adjustable countdown at rest is handed to the deck (`wheelKey`) instead
    of receiving pictures;
  - a tap starts it, and the first `LIVE` picture ends the wheel;
  - on firmware without `wheel=1` the app-stepped wheel remains.
  - The preview draws the same drum with the shared `drumRow` sums.
  - The feel constants travel in the look, so tuning needs no reflash.
- **Tests:** spec round trip and rejection, the drum geometry, and the whole
  arm, settle, swipe and tap cycle against the simulated deck.
- **Not yet seen with a real finger or the real app:** the user was away.

## The deck restarted itself; the volume arc

- **The restart:** on starting the app the deck restarted, the app logged
  `the deck did not answer` and then `error code 31`, and after that it no
  longer found the deck. Error 31 is the CH340 USB adapter wedged: only a replug
  brought it back, and a flash could not reach it until then.
- **Not a firmware crash.** The core dump partition was empty after it. To know
  whether an empty partition means anything, a deliberate `abort()` build was
  flashed and made to crash: it left a dump that decoded to the right line, so
  this build does write dumps. The first restart was therefore most likely power
  (a brownout or dip), which also fits the adapter wedging. The test dump was
  erased afterwards and the test command removed before the final flash.
- **Diagnostics now in place:** `reset=` in `ID` (why the deck last started);
  `%APPDATA%/Decky/deck.log`, recording crash, watchdog and brownout restarts, a
  deck that started again while connected, uploads it did not answer, and stray
  lines it printed; the Disconnected screen tells you to replug when Windows
  reports the adapter not working. How to read a dump is in the firmware README.
- **Volume arc:** at 56% a white stretch showed again near the end of the arc.
  The fill map measured each pixel's angle from the arc's start but wrapped it
  at the wrong point, so the last part of the arc read as near 0% and filled at
  any level. Now it wraps in the middle of the gap. A test pins it, and the deck
  showed 0/20/56/85/100 correctly. Dials already on the deck keep the old map
  until the app restarts and sends the new look.
- **Also:** die speed and bounce are bounded on both sides (an unbounded look
  could make the physics run away).
- **Checks:** typecheck, lint, 133 tests, UI, connection and package checks
  pass. The firmware on the deck is the final build; it answers `reset=poweron`.
- **Still not proven:** why the power dipped. If it happens again, `deck.log`
  will say `brownout` or `panic`.

## Firmware in folders and classes

- **Asked:** before others try Decky in a week, split the firmware's two big
  files into folders (buttons/, security/...) with object-oriented, expandable
  code; the app's main process too. Approved structure: deck/, protocol/,
  pages/, display/, input/, keys/ (drum/, dial/, die/, text/), storage/,
  network/, security/, common/, with one `Deck` owning all of it. The buttons
  folder is `keys/`, as the code calls them.
- **Checkpoint first:** three local commits (firmware, app, notes), signed, not
  pushed.
- **Proof it changed nothing:** before touching the code, a golden run on the
  deck recorded 59 replies and two screen captures for a fixed pass through
  every command. The restructured build gave identical replies and
  pixel-identical captures. Die 52-55 fps and drum 70-80 fps, as before.
  - The run is now `tools/golden_run.py` with its fixtures
    ([[firmware-golden-run]]).
  - It had to restart the deck first. Without that, a copy left in RAM, and ON
    pictures on the card, changed two replies between identical builds.
- **Shape:**
  - Each animated kind is a `Look` subclass (what the desktop sends) and a
    `KeyAnimation` (how it moves and draws).
  - Each area's commands are a `CommandSet` behind a router.
  - RAM: 92.7 KB static before, 69.2 KB now, since looks are made as needed.

- **One accepted change:** commands are routed by their first word. Garbage like

## The card save off the edit

- **Asked:** a small freeze is left when a widget's style changes. The user
  proposed a "begin upload" message, a spinner on the deck key and every key
  disabled meanwhile.
- **Found:** the freeze the user sees is on the deck. `COMMIT` saved the whole
  page to the card inside the main loop, before drawing it: 548-569 ms for a
  one-key edit and for a whole page alike, with no touches or frames meanwhile.
  A spinner could not have turned during it. The app redraws the page on the
  window's thread (up to 0.3 s), but the user does not notice that.
- **Chosen (the user):** remove the freezes rather than signal them.
- **Done:** `COMMIT` draws first, then `artwork_store` saves in steps (open, 8
  KB slices, swap) run once per loop pass. One save at a time; loading, `SDINFO`
  and `PageCache::start` finish it first. A failed save shows as `stored=0` in
  the next `COMMIT` reply.
- **Measured on the deck:**
  - `COMMIT` replies in 6 ms, down from 569.
  - A small edit takes 66-86 ms from `CACHE` to the reply.
  - During the save `PING` answers every 11-13 ms, a few times up to 45 ms.
  - After a restart the page loads from the card (`cached=1 storage=sd`).
  - The golden run is identical.
- **Not done:** the app-side parts of the approach (drawing off the window's
  thread, a spinner on the app's key tile for long uploads). The user does not
  see an app freeze.
- **Asked next:** the microphone widget with the volume's arc and bar styles.

## Double and triple taps

- **Asked:** double and triple taps, starting with Now playing: a double tap
  skips to the next track. The user chose widgets only (not per-key actions in
  the editor), and a hold on Now playing now goes back a track.
- **Built, in the app only:** the deck already reports each finger down and up,
  and its 120 ms press gap is measured press to press, so a double tap's second

    finished leaves nothing behind.

    (`media-previous` in the Windows helper).
- **The cost:** a single tap on Now playing plays or pauses 300 ms after the
  finger lifts. Every other key is as it was.
- **Checked:** typecheck, lint, 148 tests (new: one, two and three taps, a hold
  after a tap, slow taps, a widget that acts at once), build, UI and connection
  checks. The helper still answers; `media-previous` was not sent, since it
  would have skipped the user's music. Not yet tried on the deck.

## The Recording key that kept counting

- **Reported:** after the "stopping REC" countdown, the key went on showing the
  recording's time, though OBS had stopped.
- **Evidence, from OBS's own log** (`%APPDATA%\obs-studio\logs`):
  - Decky's link stayed up from 19:38:27 to 19:41:14.
  - Recording Start at 19:39:08, Recording Stop at 19:39:19. So the stop arrived
    and worked.
- **Cause:** on every output event Decky asked OBS for the status again. A stop
  sends "stopping" and "stopped" a millisecond apart. obs-websocket answers
  requests on a pool of threads, so an answer from before the stop can come last
  and keep the key running. A test with a stale status answer reproduced it: it
  failed before the fix.
- **Fixed:** the keys follow the events themselves, which come in order
  (`STATES`: started, stopped, paused, resumed, reconnecting). The time is kept
  from them. The status is asked for only as the link opens. 165 tests, UI and
  connection checks.
- **Also in OBS's log:** "Stream output type 'rtmp_output' failed to start!" at
  19:39:57. OBS itself could not start a stream; nothing was set up to stream
  to.

## Smooth rings: the deck moves their arcs (SWEEP)

## A 10-second countdown on the Debug page is "not that smooth"

- **Found by reading the loop:** the arc is only redrawn from the deck's main
  loop, and the loop was held still in three places:
  - `Screen::resync()` waited for the next VSYNC every 200 ms: up to a frame
    (18.5 ms), five times a second, on every page.
  - A picture for a key of the page shown waited for the beam to clear that key
    (`draw_key`, up to two frames), doing nothing else. The Debug page's 8 live
    widgets bring several such pictures a second.
  - During a transfer, overlays were drawn at most every 15 ms, with touch. A
    hold longer than the ~14 ms a frame leaves between the beam's passes over
    the ring skips a frame: the end sits still, then jumps.
- **Fixed:** the panel's VSYNC interrupt stamps the time
  (`Bus_RGB::lastVSyncMicros`, in the LovyanGFX patch; `panel::last_vsync_us`),
  so `resync()` never waits. `draw_key` draws other keys' overlays while it
  waits for the beam. `between_blocks` draws overlays on every idle poll; touch
  and animations stay every 15 ms. `DISPLAY_STATE` gains `gap=`, the longest the
  loop went without looking at overlays since last asked.
- **Checked:** compiled. Not measured on the deck: the user tests.

## Uneven steps on a 10-second countdown

- **Reported:** the ring stepped unevenly - "20%, then 5%, then another random",

## Why a waiting notification is not on the Notifications key

- **Reported:** Discord showed 1 notification; the key showed none.
- **Found:** not a bug in Decky. The user authorized again at 23:52 (after
  the notifications scope was added at 23:23), so the key has permission and
  subscribes. Discord's client (datamined: NotificationStore's MESSAGE_CREATE,
  RPCServerManager's handleNotificationCreate) sends NOTIFICATION_CREATE only
  for a new message that would notify, not while its window is focused and not
  while a game with its overlay is in front. No RPC command reads unread
  counts. The window title carries no count; the taskbar button's help text is
  Windows' own ("0 notifications"). A notification from before the link can
  never reach the key.
- Nothing changed in the code. Offered: keep the count across Decky
  restarts.

## Older notifications: asked, not possible; the count kept instead

- **Asked:** could the key fetch older notifications and mentions, surviving
  a Discord restart, sleep, or a Decky restart?
- **Found:** no RPC command reads read state or mention counts. `GET_CHANNEL`
  (datamined chunk 90924) fetches a channel's last messages but carries no
  read state, and DMs cannot be listed over RPC. Discord's REST API with the
  user's own account token could, but that is self-botting against Discord's
  terms: refused.
- **Built:** the key's count, last sender and channel are kept in
  `integrations/discord.json` beside the token (`keep()`, one write at a
  time; `inboxOf` reads it back). A restart of Decky or Discord keeps the
  count; notifications that come while Decky is not linked are still missed.
  Test: a second service on the same file shows the count.
- The console text the user pasted ("Quitting secondary instance", a
  punycode warning, "blackbox") is Discord's second copy, started by Decky
  to bring Discord up, handing over and quitting. It reaches the dev terminal
  because Update.exe attaches to its parent's console. Harmless; none in a
  packaged Decky.
