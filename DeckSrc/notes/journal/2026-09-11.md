# 2026-09-11

Decky 0.2.4 with firmware 0.1.3 released overnight: 6 min 43 s end to end,
including a cold-cache firmware build. It has four files: the installer (106.3
MB), its blockmap, `latest.yml` and the firmware zip.

The README plays the demo video. GitHub strips `<video>` tags pointing into the
repository, so the user uploaded it as a GitHub attachment instead. The upload
was compressed from 41 MB to 9.3 MB (720p60, SSIM 0.998) to fit the 10 MB limit
for attachments on free accounts. Both MP4s were committed by the user anyway.

## First install over factory firmware

The board was restored to Elecrow's factory firmware from
`factory-backup/crowpanel7-factory-4MB.bin`, leaving NVS alone so Wi-Fi and
pairing survived. The factory image boots its LVGL Widgets Demo and never
answers `ID`. Its partition table differs from Decky's: app0 is 3840 KB against
2048 KB, with NVS at the same place.

What the user saw, and what changed:

- **The card showed up 12-16 s after plugging in.** A silent port is now asked
  twice a second apart within one status check, and a newly plugged-in port
  triggers a check within a second. Estimated now: about 6 s, with Wi-Fi tried
  first for a paired deck.
- **Four steps became one question,** "Install Decky on this device?". The click
  checks it is a CrowPanel and installs; anything else is left untouched. It
  still waits for the click, because the check restarts the device. The card was
  redesigned, and "Looking for Decky…" hides while it shows.
- **The install message showed the git version.** It now uses the same plain
  number as the rest of the app; `formatVersion` moved to
  `src/shared/firmware.ts`.

## The picture slip, found

After the first install the picture sat 48 lines too high, wrapped. On the
slipped deck, `DISPLAY_RESYNC` (`esp_lcd_panel_init`) left it shifted, which
disproved the earlier realign theory.

Diagnostic firmware read the RGB driver's private bookkeeping at every VSYNC:

- **Correct state:** `pos=76800`, 10 EOFs per frame, even count.
- **Provoking it:** random 30 ms flash erases on the unused data partition
  showed frames losing EOFs (as few as 1 per frame). By the second stall the
  picture stayed slipped, with an odd count and nothing else different.
- **Nudging the count by one** straightened it, confirmed on the screen.

The v5.5.4 source explains why the slip lasts: with RESTART_IN_VSYNC, the driver
never zeroes the count. The fix zeroes it in our VSYNC callback. It survived 40
random stalls with 75 corrections, and a first install through the app now
leaves the picture straight, confirmed by the user. The old realign calls are
gone; `DISPLAY_STATE` stays for diagnosis. The user had also found a forum
thread describing the same drift and blaming bounce-buffer synchronisation. See
[[2026-09-11-bounce-parity-guard]].

## Page switching

The user felt page switches as "not instant". Measured with a temporary benchmark on the deck, a full page redraw took 83 ms. About 45 ms of that was copying: each key was copied pixel by pixel with an integer division per pixel. The rest was waiting on the beam. Two firmware changes:

- **Line-by-line copy:** each key row goes with one memcpy (or a column table for off-size cells). That brought the redraw to 61 ms; a key write now costs about 2.1 ms, the PSRAM-to-PSRAM floor beside the scanout.
- **Greedy order:** keys are drawn as soon as their row is clear of the beam, instead of in index order. That brought it to 35 ms.

The write estimate now eases back down instead of only ratcheting up. `DISPLAY_STATE` reports the last redraw as `draw=`. The user confirmed switches feel instant.

Back-to-Home still lagged slightly. With protocol 4 and later, opening a page was `CACHE`, then an `ALT` check per toggle key, then `STATE`, each a Wi-Fi round trip: 4 for Home with two Discord toggles, against 2 for other pages. The app now remembers the pages and the ON artwork it confirmed on the deck this session, and opens those with a single `STATE`. If the deck has dropped the page, `STATE` is refused and the full exchange runs.

## Widgets

Widget keys: clock (digital, analog or minimal; 12/24-hour; seconds; date; time
zone), timer, pomodoro, countdown, counter, ping and note, each with its own
settings, under a Widgets group in the action picker. The desktop draws them.
Pages carry time-free base pictures, and the deck gets `LIVE` tile patches
while a page is shown. Firmware 0.1.4-dirty on COM5 reports `live=1` and passed
a hardware script: 21 ms for a small patch, about 94 ms for the worst seconds
change, and a wrong base refused. A critic reviewed the transport; see
[[2026-09-11-widgets-live-patches]].

Feedback from the user testing it in the dev app:

- **12-hour time dropped the leading zero** ("2:39" beside "02:39"). Hours are
  two digits in both formats now, in the minimal style too.
- **A moved widget appeared twice on the deck,** once in the app. A digital
  clock's base picture is only its background, like an empty key's, so the
  move changed neither the page's signature nor any picture. The deck's copy
  kept the clock drawn by patches. The app now tracks patched keys per deck
  copy: it re-sends them on rebuilds and restores them on cached pages. A
  simulated-deck test reproduces the bug.
- **Holds waited for the release.** A hold now acts the moment the press
  reaches 600 ms, so a stopwatch shows its reset under the finger.
- **"Server status" became "Ping"**, for everyday use. ICMP to the internet
  never answers on this PC, which is behind a VPN adapter, while TCP to port
  443 answers in 16-46 ms. So the widget times a TCP handshake, with a second
  one raced after 500 ms because 1 handshake in 30 was lost, and falls back to
  ping.exe for hosts that answer no TCP. The router answered that way in 1 ms.

## Countdown wheel and the picker

- **Countdown set on the deck.** A timer in countdown mode can have "Set time on
  the deck". At rest its key shows a picker wheel, and a swipe steps it every
  15 px: 10 s steps to a minute, minutes to an hour, 5 minutes to 3 hours. The
  user chose this design (a wheel on the key, snapping steps, adaptive steps)
  over a multi-key picker page and a smooth scroll run on the deck.
  - **Firmware:** `DRAG <mask>` plus `EV … MOVE <y>`, gated by `drag=1`.
    Released apps would take an unknown `EV` line as a command's reply, so the
    deck reports movement only for keys the app names.
  - **Measured:** a wheel step's patch is 0.8-3 KB, about 40-130 ms over USB,
    so live frames are now coalesced per key.
  - **First try on the deck:** swiping started the countdown. The deck still
    had the old firmware, with no `MOVE`, so every touch was a tap. Flashed:
    `ID` shows `drag=1` and `DRAG` answers `OK drag`.
  - **Tests:** a simulated-deck test covers swipe, tap and a swipe while it runs.
- **Picker.** Widgets moved behind a Widgets row with its own panel and Back.
  After picking, a ‹ in the editor returns to the panel the choice was made in,
  until the key is first saved.

## The wheel moves onto the deck

The user wanted the countdown wheel to follow the finger in real time, with
iPhone-style momentum and snapping. App-drawn steps "teleported": each patch
takes 40-130 ms over USB. The user set a rule: animated or heavy keys run on
the deck, static or occasional ones in the app ([[deck-first-for-animation]]).

- **Built:** `firmware/src/wheel.cpp`.
  - **The look:** the desktop sends it once (`WHEEL`). It holds the key picture
    under the numbers as a `LIVE` patch, the digits at two sizes rasterised in
    the app's Segoe UI (not embedding the font), the 89 labels, and the drum
    and physics settings. The deck keeps four looks by CRC, and `WHEELAT`
    re-arms one with a single line.
  - **Drawing:** the deck draws a drum (labels at `row/angle · sin θ`, squashed
    by `cos θ`, faded by `cos² θ`) that follows the finger 1:1.
  - **Motion:** a flick glides with exponential decay (τ 0.32 s) until below
    4 labels/s. A critically damped spring (ω 16) then lands it on a label,
    and it bounces at the ends. It reports `EV … WHEEL <label>` when it stops.
  - **Tearing:** frames are composed before the beam check, so only the copy
    has to fit between the beam's passes.
- **Measured on the deck** with the real 15 KB look generated by the app's code:
  - the upload took 1.06 s over USB; each frame composes in 4.3 ms, at 61-67 fps;
  - `WHEELSPIN` +30/s moved 9 labels and settled in 1.08 s;
  - −60/s ran into the start, bounced and settled in 1.22 s;
  - a mid-spin screen capture shows two rows straddling the band, so the
    motion is continuous, not stepped.
- **App:**
  - an adjustable countdown at rest is handed to the deck (`wheelKey`) instead
    of receiving pictures;
  - a tap starts it, and the first `LIVE` picture ends the wheel;
  - on firmware without `wheel=1` the app-stepped wheel remains.
  - The preview draws the same drum with the shared `drumRow` sums.
  - The feel constants travel in the look, so tuning needs no reflash.
- **Tests:** spec round trip and rejection, the drum geometry, and the whole
  arm, settle, swipe and tap cycle against the simulated deck.
- **Not yet seen with a real finger or the real app:** the user was away.

## Countdown sound

- **The sound:** the user wanted a soft, looping sound when a countdown ends,
  played by the PC. Five synthesised candidates went to them as WAV files
  (soft bell, glass fifth, kalimba, ding-dong, airy chime); they rejected a
  listening page and picked the kalimba.
- **Built:** countdowns have "Sound when it ends", on by default.
  - **Looping:** `kalimba.wav` is one 2-second cycle, its tail faded to
    silence, and loops until the key is tapped.
  - **Stopping:** a tap on an ended countdown now resets it (it used to
    restart it) and stops the sound.
- **Checks:**
  - The UI check pushes an ended countdown into the app and checks the kalimba
    starts, then that resetting stops it.
  - `pnpm package` confirmed the `.wav` ships.

## The deck restarted itself; the volume arc

- **The restart:** on starting the app the deck restarted, the app logged
  `the deck did not answer` and then `error code 31`, and after that it no
  longer found the deck. Error 31 is the CH340 USB adapter wedged: only a
  replug brought it back, and a flash could not reach it until then.
- **Not a firmware crash.** The core dump partition was empty after it. To
  know whether an empty partition means anything, a deliberate `abort()` build
  was flashed and made to crash: it left a dump that decoded to the right line,
  so this build does write dumps. The first restart was therefore most likely
  power (a brownout or dip), which also fits the adapter wedging. The test
  dump was erased afterwards and the test command removed before the final
  flash.
- **Diagnostics now in place:** `reset=` in `ID` (why the deck last started);
  `%APPDATA%/Decky/deck.log`, recording crash, watchdog and brownout restarts,
  a deck that started again while connected, uploads it did not answer, and
  stray lines it printed; the Disconnected screen tells you to replug when
  Windows reports the adapter not working. How to read a dump is in the
  firmware README.
- **Volume arc:** at 56% a white stretch showed again near the end of the arc.
  The fill map measured each pixel's angle from the arc's start but wrapped it
  at the wrong point, so the last part of the arc read as near 0% and filled at
  any level. Now it wraps in the middle of the gap. A test pins it, and the
  deck showed 0/20/56/85/100 correctly. Dials already on the deck keep the old
  map until the app restarts and sends the new look.
- **Also:** die speed and bounce are bounded on both sides (an unbounded look
  could make the physics run away).
- **Checks:** typecheck, lint, 133 tests, UI, connection and package checks
  pass. The firmware on the deck is the final build; it answers `reset=poweron`.
- **Still not proven:** why the power dipped. If it happens again, `deck.log`
  will say `brownout` or `panic`.
