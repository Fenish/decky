# 2026-09-11

Decky 0.2.4 with firmware 0.1.3 released overnight: 6 min 43 s end to end,
including a cold-cache firmware build. It has four files: the installer (106.3
MB), its blockmap, `latest.yml` and the firmware zip.

The README plays the demo video. GitHub strips `<video>` tags pointing into the
repository, so the user uploaded it as a GitHub attachment instead. The upload
was compressed from 41 MB to 9.3 MB (720p60, SSIM 0.998) to fit the 10 MB limit
for attachments on free accounts. Both MP4s were committed by the user anyway.

## First install over factory firmware

The board was restored to Elecrow's factory firmware from
`factory-backup/crowpanel7-factory-4MB.bin`, leaving NVS alone so Wi-Fi and
pairing survived. The factory image boots its LVGL Widgets Demo and never
answers `ID`. Its partition table differs from Decky's: app0 is 3840 KB against
2048 KB, with NVS at the same place.

What the user saw, and what changed:

- **The card showed up 12-16 s after plugging in.** A silent port is now asked
  twice a second apart within one status check, and a newly plugged-in port
  triggers a check within a second. Estimated now: about 6 s, with Wi-Fi tried
  first for a paired deck.
- **Four steps became one question,** "Install Decky on this device?". The click
  checks it is a CrowPanel and installs; anything else is left untouched. It
  still waits for the click, because the check restarts the device. The card was
  redesigned, and "Looking for Decky…" hides while it shows.
- **The install message showed the git version.** It now uses the same plain
  number as the rest of the app; `formatVersion` moved to
  `src/shared/firmware.ts`.

## The picture slip, found

After the first install the picture sat 48 lines too high, wrapped. On the
slipped deck, `DISPLAY_RESYNC` (`esp_lcd_panel_init`) left it shifted, which
disproved the earlier realign theory.

Diagnostic firmware read the RGB driver's private bookkeeping at every VSYNC:

- **Correct state:** `pos=76800`, 10 EOFs per frame, even count.
- **Provoking it:** random 30 ms flash erases on the unused data partition
  showed frames losing EOFs (as few as 1 per frame). By the second stall the
  picture stayed slipped, with an odd count and nothing else different.
- **Nudging the count by one** straightened it, confirmed on the screen.

The v5.5.4 source explains why the slip lasts: with RESTART_IN_VSYNC, the driver
never zeroes the count. The fix zeroes it in our VSYNC callback. It survived 40
random stalls with 75 corrections, and a first install through the app now
leaves the picture straight, confirmed by the user. The old realign calls are
gone; `DISPLAY_STATE` stays for diagnosis. The user had also found a forum
thread describing the same drift and blaming bounce-buffer synchronisation. See
[[2026-09-11-bounce-parity-guard]].

## Page switching

The user felt page switches as "not instant". Measured with a temporary benchmark on the deck, a full page redraw took 83 ms. About 45 ms of that was copying: each key was copied pixel by pixel with an integer division per pixel. The rest was waiting on the beam. Two firmware changes:

- **Line-by-line copy:** each key row goes with one memcpy (or a column table for off-size cells). That brought the redraw to 61 ms; a key write now costs about 2.1 ms, the PSRAM-to-PSRAM floor beside the scanout.
- **Greedy order:** keys are drawn as soon as their row is clear of the beam, instead of in index order. That brought it to 35 ms.

The write estimate now eases back down instead of only ratcheting up. `DISPLAY_STATE` reports the last redraw as `draw=`. The user confirmed switches feel instant.

Back-to-Home still lagged slightly. With protocol 4 and later, opening a page was `CACHE`, then an `ALT` check per toggle key, then `STATE`, each a Wi-Fi round trip: 4 for Home with two Discord toggles, against 2 for other pages. The app now remembers the pages and the ON artwork it confirmed on the deck this session, and opens those with a single `STATE`. If the deck has dropped the page, `STATE` is refused and the full exchange runs.
