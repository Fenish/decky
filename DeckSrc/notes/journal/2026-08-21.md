# 2026-08-21

## Starved keys, twice, from the same mistake

Keys reported as stuttering: the bottom row rough while the top two were smooth,
then the last keys down to one frame a second and sometimes none at all.

Both were the same bug in two places, and neither was what it looked like.

The first: the main loop served keys in index order, and the panel's scanout
beam also runs top to bottom. By the time a pass reached the bottom row the beam
was late in the frame - exactly when that row is unsafe to write - so those keys
were deferred pass after pass. Ordering by lateness instead of by index removed
the bias.

The second only became visible after adding a per-key report, and the totals had
been hiding it completely: a deck averaging 16 fps had four keys streaming from
the card, one getting 24 fps and three getting **zero**. The card reader also
walked keys in index order, and one full-size streamed key needs 357 KB/s of the
383 KB/s the card provides - so the first key took everything. Serving the most
overdue key each time round gave 6 fps each instead.

Worth keeping: I diagnosed the first one correctly from the description, then
assumed the second was more of the same and was wrong. The per-key numbers took
a minute to add and settled in one reading what three rounds of reasoning had
not. Averages hide starvation by construction.

## Card access needed a lock

Uploading while a key streamed corrupted the transfer at 99% with
ESP_ERR_INVALID_CRC. Two cores were using the card at once - the reader pulling
frames, the upload writing a file - and neither the SDSPI driver nor the FAT
layer tolerates that. Every path that touches the card now takes one recursive
mutex. Uploads hold it for the whole file, so streamed keys freeze while one is
in progress; a pause is a better trade than a corrupted file.

## Also today

The deck now answers `ID` with its own name, protocol version, MAC and key
geometry, so the desktop app can identify it rather than guessing from the USB
chip - which had been reporting the machine's built-in COM1 as a connected deck.
The geometry comes from the device so the layout is described in one place.

Content fills each key edge to edge now: the alignment outlines are gone, and
the host crops to the key's proportions rather than fitting a square inside it.

Boot shows progress on the middle key. Reading fifteen keys off the card takes
several seconds with the backlight already on, and a blank grid for that long
looks like a deck that failed to start.

The SD mount at boot now retries five times. A single attempt failed often
enough that keys came up on their built-in animations while the same card
mounted fine moments later.
