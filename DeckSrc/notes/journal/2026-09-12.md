## App control keys look disabled while their app is out of reach

- **Asked:** while Discord is not connected, every Discord key should look
  disabled - grey, with the slash the widgets already had.
- **Built:**
  - `strike()` in `canvas-kit.ts`: the one slash (grey, cut from what is
    under it by a gap). Discord's widgets, OBS's keys and plain keys use it;
    OBS's look is unchanged.
  - `renderKey(..., disabled)`: the icon grey at 45 % and struck, the label
    grey, an image desaturated and darkened with a slash. `pageFrames` and
    `pageToggleFrames` take the apps down; `keyDisabled` and `downOn` say
    which keys and pages that touches.
  - `useAppsDown(config)`: the window asks each controlled app's standing once
    and follows `integration:status`; an app not heard of counts as
    reachable. `useDecky` puts the page's apps down into its bitmap and sync
    tokens, so the shown page is sent again (only the keys that changed) and
    other pages follow as they open. The dashboard's key faces use it too.
  - Found on the way: `ArtworkPreview` left out `iconSize`, so the window's
    previews of plain keys ignored Icon size while the deck followed it.
    Fixed.
- **Checked:** typecheck, lint, prettier, 198 tests, the UI check. Plain keys
  rendered normal and disabled (no label, 160 %, coloured background, images)
  beside a Discord widget out of reach, and looked at. Not tried on the deck:
  the user tests.

## The freeze when Discord went and came back

- **Reported:** after quitting Discord and opening it again, things froze at
  first - like the first mute press used to.
- **Found:** my disabled look changed every Discord toggle's ON picture too.
  The deck takes ON pictures (`ALT`) only whole, does not carry them into a
  new page version, and reloads one from its card only by the same checksum -
  the card keeps one per key. So each change of Discord's reach sent every
  toggle's ON picture again, 29 KB each: with 8 Discord toggles about 250 KB
  over USB, several seconds with the deck and the serial queue busy - both
  when Discord went and when it came back.
- **Fixed:** only the OFF picture is drawn disabled. `DiscordService`
  reports no control state while Discord is out of reach (camera and share
  included), so its toggles show OFF, and the ON pictures never change.
  Measured: normal to disabled is a 1.5-3 KB patch per key (Mute 2016 B,
  back 1537 B), about 20 KB for 8 keys.
- The deck may hold the disabled ON pictures the earlier build sent: the
  first sync after this one sends the normal ones once more.
- **Checked:** typecheck, lint, prettier, 198 tests. Not tried on the deck:
  the user tests.

## Device switchers came back in two steps

- **Reported:** after Discord reopened, every Discord key came back at once,
  but the mic and output switchers changed twice.
- **Found** (Discord's client, datamined chunks 90924 and 217090): the RPC's
  voice settings carry the device in use from Discord's saved settings, but
  `available_devices` from its media engine, which lists devices a moment
  after Discord starts. VOICE_SETTINGS_UPDATE is sent at once on SUBSCRIBE
  and again whenever the settings differ, so the list arrived in a second
  update. The switchers drew the first as "reachable, no device" (the icon
  alone), then the device.
- **Fixed:** a switcher stays out of reach while Discord is ready but has no
  device list for its flow. Test: every state the key shows while the list
  arrives late - one change to "ready" (without the fix, two).
- **Checked:** typecheck, lint, prettier, 199 tests.

## Switchers again; Mute while deafened; choice keys

- **Reported:** the mic switcher still changed twice: icon and "Default",
  then disabled, then the real device.
- **Found** (Discord's client: MediaEngineStore, chunk 430452; the id in
  731854): before its media engine lists devices, Discord's list holds one
  stand-in, id `"default"` - the default device's id - named "No Input
  Devices" and marked disabled, which the RPC drops. So the first list was
  not empty, and the earlier fix (empty list) missed it. The disabled step in
  between cannot come from the list (never empty over RPC), so the link most
  likely dropped once while Discord started. Not seen directly: nothing
  recorded it.
- **Fixed:** a list is "listed" only with more than the stand-in; until then
  the switcher stays out of reach. The test now uses the stand-in; it fails
  with the earlier check.
- **Added:** `discord.log` (`LogFile`, deck.log's code made general): link
  up, how long it lived, Discord's standing when it changed, and each flow's
  device count and the device in use when they change. If a Discord start
  still flickers, it will say whether the link dropped.
- **Asked:** Mute should show muted while deafened. Discord's `isSelfMute`
  counts deafened as muted, but the RPC reports the stored `mute`. Mute's
  state is now `mute` or `deaf`, and a press asks for the opposite of what
  it shows: mute off while deafened, which undeafens, as Discord's own
  button does.
- **Asked:** are the switchers' cycling and dots generic? They were not.
  Now: `shared/widgets/choice.ts` (`Choice`, `choiceOf`, `nextChoice`) and
  the renderer's `choice-face.ts` draw any key whose state has a `choice`;
  the key's own icon helpers moved to `key-glyph.ts`. The Discord switchers
  use them.
- **Checked:** typecheck, lint, prettier, 201 tests, the UI check.

## Back from a page opened elsewhere; "Invalid toggle artwork"

- **Reported:** with the Discord and OBS pages opened from keys on the Debug
  page, Back went to Home. And main logged `Error occurred in handler for
  'pages:cache': Invalid toggle artwork`.
- **Back, found:** Back went to the page's parent, the page it was created
  under. Nothing in the window moves a page under another, so pages made at
  Home and opened from Debug went back Home.
- **Back, changed:** `Workspace` remembers, for each page opened (by a page
  key, or the window), the page it was opened from; Back (the deck's key 11,
  the window's, `page:back`) goes there, else to the parent. Not kept across
  a restart.
- **The error, found:** saving the profile does not wait behind page uploads,
  which queue one after another (`session.serial`). An upload drawn before a
  save that added or removed a toggle key (or a page) reached main after it,
  and its ON pictures no longer matched the profile: thrown as an error, though
  the window draws and sends everything again for the new profile anyway.
- **The error, changed:** such a request is answered `{ ok: false, stale:
  true }` (the pages' ids, or a page's toggle cells, differ from the profile
  now); malformed requests still throw. The window says nothing for a stale
  reply. `Reply.stale` is new.
- **Checked:** typecheck, lint, prettier, 203 tests (new, on the simulated
  deck: a stale cache request; Back through Debug and Home), the UI check.
