## The freeze when Discord went and came back

- **Reported:** after quitting Discord and opening it again, things froze at
  first - like the first mute press used to.
- **Found:** my disabled look changed every Discord toggle's ON picture too.
  The deck takes ON pictures (`ALT`) only whole, does not carry them into a
  new page version, and reloads one from its card only by the same checksum -
  the card keeps one per key. So each change of Discord's reach sent every
  toggle's ON picture again, 29 KB each: with 8 Discord toggles about 250 KB
  over USB, several seconds with the deck and the serial queue busy - both
  when Discord went and when it came back.
- **Fixed:** only the OFF picture is drawn disabled. `DiscordService`
  reports no control state while Discord is out of reach (camera and share
  included), so its toggles show OFF, and the ON pictures never change.
  Measured: normal to disabled is a 1.5-3 KB patch per key (Mute 2016 B,
  back 1537 B), about 20 KB for 8 keys.
- The deck may hold the disabled ON pictures the earlier build sent: the
  first sync after this one sends the normal ones once more.
- **Checked:** typecheck, lint, prettier, 198 tests. Not tried on the deck:
  the user tests.

## Device switchers came back in two steps

- **Reported:** after Discord reopened, every Discord key came back at once,
  but the mic and output switchers changed twice.
- **Found** (Discord's client, datamined chunks 90924 and 217090): the RPC's
  voice settings carry the device in use from Discord's saved settings, but
  `available_devices` from its media engine, which lists devices a moment
  after Discord starts. VOICE_SETTINGS_UPDATE is sent at once on SUBSCRIBE
  and again whenever the settings differ, so the list arrived in a second
  update. The switchers drew the first as "reachable, no device" (the icon
  alone), then the device.
- **Fixed:** a switcher stays out of reach while Discord is ready but has no
  device list for its flow. Test: every state the key shows while the list
  arrives late - one change to "ready" (without the fix, two).
- **Checked:** typecheck, lint, prettier, 199 tests.

## Switchers again; Mute while deafened; choice keys

- **Reported:** the mic switcher still changed twice: icon and "Default",
  then disabled, then the real device.
- **Found** (Discord's client: MediaEngineStore, chunk 430452; the id in
  731854): before its media engine lists devices, Discord's list holds one
  stand-in, id `"default"` - the default device's id - named "No Input
  Devices" and marked disabled, which the RPC drops. So the first list was
  not empty, and the earlier fix (empty list) missed it. The disabled step in
  between cannot come from the list (never empty over RPC), so the link most
  likely dropped once while Discord started. Not seen directly: nothing
  recorded it.
- **Fixed:** a list is "listed" only with more than the stand-in; until then
  the switcher stays out of reach. The test now uses the stand-in; it fails
  with the earlier check.
- **Added:** `discord.log` (`LogFile`, deck.log's code made general): link
  up, how long it lived, Discord's standing when it changed, and each flow's
  device count and the device in use when they change. If a Discord start
  still flickers, it will say whether the link dropped.
- **Asked:** Mute should show muted while deafened. Discord's `isSelfMute`
  counts deafened as muted, but the RPC reports the stored `mute`. Mute's
  state is now `mute` or `deaf`, and a press asks for the opposite of what
  it shows: mute off while deafened, which undeafens, as Discord's own
  button does.
- **Asked:** are the switchers' cycling and dots generic? They were not.
  Now: `shared/widgets/choice.ts` (`Choice`, `choiceOf`, `nextChoice`) and
  the renderer's `choice-face.ts` draw any key whose state has a `choice`;

- **Checked:** typecheck, lint, prettier, 201 tests, the UI check.

## Back from a page opened elsewhere; "Invalid toggle artwork"

- **Reported:** with the Discord and OBS pages opened from keys on the Debug
  page, Back went to Home. And main logged `Error occurred in handler for
'pages:cache': Invalid toggle artwork`.
- **Back, found:** Back went to the page's parent, the page it was created
  under. Nothing in the window moves a page under another, so pages made at
  Home and opened from Debug went back Home.
- **Back, changed:** `Workspace` remembers, for each page opened (by a page
  key, or the window), the page it was opened from; Back (the deck's key 11,
  the window's, `page:back`) goes there, else to the parent. Not kept across
  a restart.
- **The error, found:** saving the profile does not wait behind page uploads,
  which queue one after another (`session.serial`). An upload drawn before a
  save that added or removed a toggle key (or a page) reached main after it,
  and its ON pictures no longer matched the profile: thrown as an error, though
  the window draws and sends everything again for the new profile anyway.
- **The error, changed:** such a request is answered `{ ok: false, stale:
true }` (the pages' ids, or a page's toggle cells, differ from the profile
  now); malformed requests still throw. The window says nothing for a stale
  reply. `Reply.stale` is new.
- **Checked:** typecheck, lint, prettier, 203 tests (new, on the simulated
  deck: a stale cache request; Back through Debug and Home), the UI check.

## A fast unplug while loading: EPIPE, a stuck queue, blank widget keys

- **Reported:** a fast unplug and replug during the loading screen; Decky
  stayed "connected" and did not notice; `deck:live` threw EPIPE ("this
  socket has been ended by the other party"). Widget keys on the Debug page
  (counter, price, CPU and memory, now playing) showed nothing on the deck
  while the window kept drawing them, through page changes; Home's now
  playing was fine.
- **Found:** the write was on the Wi-Fi socket - the unplug had fallen back
  to it - and the deck's power went with the replug. Nothing watched that
  socket for the deck ending it, and a write to a peer that is gone waits on
  TCP's own timeouts, which are minutes. Every deck command shares one queue,
  so the PING that would have noticed waited behind it: the app went on
  believing it was connected. Meanwhile the deck came back from its card with
  the pages but no live pictures, and the app, holding a record of pictures
  the deck no longer had, sent nothing for a key whose picture had not
  changed. Not reproduced in a test: the reproduction needs the link to hang.
- **Built** (all host-side, so the deck is asked nothing more often):
  - The socket is dropped when the deck ends it ("end", "close"), and a write
    to one that is gone is refused rather than throwing EPIPE.
  - A write over Wi-Fi that takes more than 3 s counts as the link gone: it
    is rejected and the socket destroyed, so the queue moves on.
  - `DeckLink.silentFor` says how long the deck has said nothing. A ping still
    waiting while the deck has been silent for 8 s means the queue is stuck on
    a dead link: the deck counts as gone and the link closes, which frees
    everything waiting.
  - The port watch already noticed a port appear; it notices one go too, and
    the deck's own cable going means the deck is gone at once (`linkLost`).
  - A patch that fails because the deck went is no longer reported as an
    error; the window draws the key again when it is back.
  - HELLO drops every live picture on the deck, so the app now forgets its
    record of them there too (it only forgot the overlays).
- **Checked:** typecheck, lint, prettier, 204 tests (new: a load that fails
  part way, then another, leaves the widget's picture on the deck).
- Line endings: the rebase had checked the tree out as CRLF (core.autocrlf
  was true), which made Prettier fail on every file. autocrlf is off for this
  repository now and the tree is back to LF.

## The blank widget keys: the deck was out of room, and said so

- **The trace answered it the first time it happened again.** deck.log, after a
  microphone key was added to Home:
  `live home:13: the deck refused it: ERR live memory (14 since)`, forty times,
  every ten seconds, for ever. Nothing was wrong in the sending path - which is
  why the replay test passed.
- **Why:** the profile has 8 pages, 59 keys, 25 of them widgets. A key picture
  is ~118x122x2 = 29 KB, a page copy's own pictures ~430 KB, and the deck
  caches every page. `live_room()` in `page.cpp` asks for the 768 KB floor plus
  a whole page in one piece before it will allocate one 29 KB live picture, so
  live pictures stop long before PSRAM is full. The microphone key was simply
  the one that tipped it, and Home's now playing and clock went with it.
- **Firmware:** `PageCache::free_lives(keep)` - the oldest copy that is neither
  shown, nor being built, nor the one asking gives up its live pictures, and
  the key tries again. The desktop needs telling nothing: its next patch for an
  evicted key fails the base CRC and it sends the whole key.
- **Desktop, so it helps before a flash:** on `ERR live memory` Decky takes back
  the live pictures of pages that are not shown and retries, and for a minute
  after (`CROWDED_MS`) it leaves hidden pages alone rather than filling the deck
  again. What you are looking at wins.
- **Checked:** typecheck, lint, prettier, 223 tests (new: a deck with room for
  no more live pictures gives the page in front of you the last one), and the
  firmware builds.

## Several profiles, and a profile you can hand to someone

- **Asked for:** profiles beside Pages under the deck, switching only after
  looking inside, and one encrypted `.deckyprofile` that carries everything -
  scripts included - registered with Windows so a double-click offers to import
  it. And: it must catch new credentials, integrations and widgets by itself.
- **Designed** in [[2026-09-12-profiles]] against four answers: files land in
  the profile's own folder with paths rewritten, one key inside Decky
  (obfuscation, said plainly), profiles own app and integration settings, and
  an import always adds rather than replaces.
- **Built:** `profiles.ts` (the list, the folders, adopting the old
  `decky.json`), `bundle.ts` (the file format, AES-256-GCM over gzip, reading
  files a profile uses and placing them safely), `report.ts` (what the
  inspector shows), `Workspace.useProfile/offerFile/inspectFile/takeProfile`,
  the IPC and preload, and the Profiles panel with its inspector.
- **The auto-catch is compile-time**, which is the part worth keeping:
  `ACTION_FILES` and `WIDGET_FILES` are mapped types over every kind, so a new
  action or widget will not compile until it says whether it keeps files and
  whether they travel; integrations are walked from `INTEGRATIONS`, and secrets
  are found by the `secret` flag each field already had.
- **Then, asked about it:** the app now registers the file type itself when it
  is packaged (`system/file-type.ts`, four HKCU keys, written only when they do
  not already point at this exe), which also puts right a Decky that moved. Two
  things were wrong before that: nothing but the installer registered anything,
  and `resources/profile.ico` was inside the asar, where Windows cannot read it
  for the file's icon - it ships unpacked now.
- **Deleting a profile takes two presses**: the bin arms and a tick confirms,
  disarming itself after four seconds.
- **The gaps named, then closed:** every row exports itself now, so the profile
  in use is no longer the only one that can travel; an import lands on what it
  added, where the switch is one press away; and an armed bin says that
  deleting also removes the scripts the profile brought.
- **One of those "gaps" was not one.** A switch already calls
  `PageSync.forget()`, which clears `cacheInitialized`, so the next load sends
  HELLO and the deck drops the pages and live pictures of the profile left
  behind - it does not carry two profiles' pages in the memory that ran out
  yesterday. Now asserted rather than assumed.
- **Left:** the double-click has not been tried on a real install, and none of
  the profile work has met a real deck or the user's own decky.json.
- **Checked:** typecheck, lint, prettier, 238 tests (14 new across profiles,
  the bundle and a switch that keeps each profile's counters apart), and the UI
  check, which now walks Profiles.
